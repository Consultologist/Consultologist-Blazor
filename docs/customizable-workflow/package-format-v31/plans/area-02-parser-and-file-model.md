# Area 02: parser and file model (specVersion 31) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read a specVersion 31 package's files into a typed file model, or into the refusal sentences part 01 gives, in `Consultologist.PackageFormat`, with nothing in the engine calling it yet.

**Architecture:** A new folder `src/Consultologist.PackageFormat/V31/` (namespace `Consultologist.PackageFormat.V31`) holds a pipeline of four pure steps: **intake** (bytes → normalised text, `SourceBounds`), **strict JSON and front matter**, **layout** (folders, indexes, strays), and **declarations** (member tables per file kind, the flow and function shapes, scopes and keys). `SourceParser.Parse` runs them and returns a `SourcePackage` or a list of `SourceRefusal`s; it never throws on any input. Formats, expressions, prompt members, delivery settings and tests are carried as raw JSON for the areas that own them (03, 04, 05, 07, 08). The area also exports the conformance suite's first `refusal-packages` cases, generated by the parser.

**Tech Stack:** C# / .NET 10, `System.Text.Json` (`Utf8JsonReader`, `JsonNode`), xUnit in `tests/Consultologist.Api.Tests.csproj`; Python 3 for the content repo's `scripts/check-v31.py`.

**Spec:** `docs/customizable-workflow/package-format-v31/` — [`01-files-and-scopes.md`](../01-files-and-scopes.md) §§ 1–7, 9 and *Refusals*; [`04-loops-and-functions.md`](../04-loops-and-functions.md) § 1 and the member tables of §§ 2.1, 3.1, 5.1, 5.2, 7.1, 7.2, 7.2.1, 7.7; [`refusal-sentences.md`](../refusal-sentences.md). The published contract is `external/consultologist-package-format/v31/` (`bounds.json`, `sentences.json`, `schemas/`, `conformance/`). Area issue #1499, parent #1496, runbook [`BUILD-RUNBOOK.md`](../BUILD-RUNBOOK.md).

## Review Focus

1. **A Windows checkout or a zip made on Windows:** `\r\n` everywhere, a byte-order mark, `---\r\n` fences. Expected: `\r\n` is normalised before anything else, so the fences and bodies read as on Linux, and the file is named in `Normalised`; a byte-order mark gets S01-014. (Task 3, `Intake_NormalisesCrLf_BeforeTheFenceIsRead`; Task 6, `AWindowsCheckout_ParsesToTheSamePackage`.)
2. **Upload paths that are not plain:** a backslash, a leading `./` or `/`, `..`, an upper-case name, a directory entry ending in `/`, `.DS_Store`. Expected: each is a stray file (S01-006), never an exception and never a file read from elsewhere. (Task 5, `OddPaths_AreStrayFiles`.)
3. **Garbage in any one file:** each file of a valid package in turn deleted, emptied, replaced by `{}`, by `[]`, by `null`, by `---`, or by random bytes. Expected: `Parse` returns at least one refusal and never throws. (Task 8, `AnyOneFileBroken_IsRefused_AndNeverThrows`.)
4. **Many faults at once:** a package with a stray file, a missing member in one node and a bad id in another. Expected: all three sentences come back in one parse, in path order. (Task 6, `IndependentFaults_AreAllReported`.)
5. **A duplicate key or deep nesting buried inside a header:** a repeated member three levels down, or 33 arrays inside `expression`. Expected: S01-018 names the member; S01-041 gives the pointer; neither is silently "last wins". (Task 2, `DuplicateKey_AtAnyDepth_IsRefused`; `Depth33_IsRefused_WithItsPointer`.)

  - `public sealed record StrictJsonResult(JsonNode? Value, bool IsNull, StrictJsonFault? Fault, string? Detail);` — `Detail` is the parser's message, the repeated member's name, or the JSON pointer. `IsNull` tells a valid `null` document from a fault.
